# Use Case Specification for Service Platforms

Проект посвящён формализации функциональных требований через Use Case.

В качестве предметных областей рассматриваются две сервисные системы:

- онлайн-запись в барбершоп;
- доставка заказов.

Для обеих систем характерно взаимодействие нескольких ролей, изменение состояния бизнес-объектов и необходимость обработки основного и альтернативных сценариев.

Детальные Use Case в текущем репозитории разработаны для системы онлайн-записи.

## Предметные области

### Онлайн-запись

Система позволяет клиенту:
- выбрать услугу;
- выбрать мастера;
- подобрать свободное время;
- оформить запись.

Менеджер управляет расписанием и услугами, а мастер получает информацию о своих записях и обратной связи клиентов.

### Доставка

В параллельном кейсе система должна поддерживать:
- получение заказа;
- бронирование заказа курьером;
- изменение статусов;
- управление доставкой диспетчером;
- взаимодействие с бухгалтерией.

Эта предметная область использовалась как дополнительный контекст при изучении способов описания взаимодействия пользователей с информационной системой.

## Структура Use Case

Для каждого варианта использования определяются:

- ID;
- название;
- основной актор;
- цель;
- заинтересованные стороны;
- предусловия;
- триггер;
- минимальные гарантии;
- гарантии успеха;
- предположения.

Для более сложных взаимодействий используются отношения:

- `<<include>>`;
- `<<extend>>`.

Отдельно описываются основной и альтернативные потоки.

## Структура проекта

### `ex00_BARB_UC.docx`

Use Case `UC-001 — Управлять расписанием услуг мастеров`.

Основной актор — менеджер.

Цель — поддерживать актуальное расписание мастеров и перечень выполняемых ими услуг.

В документе описаны:
- интересы менеджера;
- интересы клиентов и мастеров;
- предусловия;
- триггер;
- минимальные гарантии;
- гарантии успеха.

### `ex01_BARB_UC.docx`

Детальные потоки UC-001.

Основной сценарий описывает:
- выбор мастера;
- просмотр текущего расписания;
- внесение изменений;
- подтверждение данных;
- сохранение нового расписания.

Также описаны альтернативные ситуации:
- выбор другого мастера;
- отмена редактирования;
- некорректные данные;
- отмена сохранения;
- ошибка сохранения.

### `ex02_BARB_UC.docx`

Use Case `UC-002 — Забронировать услугу мастера`.

Основной актор — клиент.

В сценарий входят:
- выбор услуги;
- выбор мастера;
- выбор времени;
- оформление записи.

Функциональность декомпозирована на дополнительные Use Case:

- `UC-003 — Выбрать услугу и мастера` — `<<include>>`;
- `UC-004 — Выбрать время записи` — `<<include>>`;
- `UC-005 — Указать/обновить контактные данные` — `<<extend>>`.

### `ex03_BARB_UC (1).docx`

Потоки сценариев бронирования.

Основной сценарий:
1. клиент открывает онлайн-запись;
2. выбирает услугу и мастера;
3. получает доступные интервалы;
4. выбирает время;
5. подтверждает запись;
6. система создаёт запись.

Альтернативные сценарии описывают:
- отсутствие подходящего мастера;
- отсутствие свободного времени;
- ситуацию, когда слот уже занят;
- необходимость ввода или корректировки контактных данных.

Отдельно описаны потоки UC-003, UC-004 и UC-005.

### `ex04_BARB_UC (1).docx`

Use Case для мастера.

Основной сценарий:
`UC-006 — Просмотреть расписание и отзывы клиентов`.

Дополнительные Use Case:

- `UC-007 — Просмотреть расписание записей` — `<<include>>`;
- `UC-008 — Просмотреть отзывы клиентов` — `<<include>>`;
- `UC-009 — Получить уведомление о новой записи` — `<<extend>>`.

Описаны ограничения доступа: мастер работает только со своими записями и может просматривать, но не изменять отзывы.

### `ex05_BARB_UC.docx`

Детальные потоки сценариев для мастера.

Рассматриваются:
- просмотр расписания;
- отсутствие записей;
- просмотр отзывов;
- отсутствие отзывов;
- получение уведомления;
- сохранение уведомления, если мастер не находится в системе.

## Результат

В результате функциональность системы описана не только как перечень требований, но и как набор конкретных взаимодействий пользователя и системы при нормальном и альтернативном развитии событий.

### Использованные подходы

`Use Case` · `Functional Requirements` · `Actors` · `Main Flow` · `Alternative Flow` · `include` · `extend`
